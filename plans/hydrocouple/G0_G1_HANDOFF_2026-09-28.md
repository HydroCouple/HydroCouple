# Hand-off: G0 (DLPack), G1 (the contract), G3-lite (torch/JAX overlays)

**Repo:** HydroCouple, branch `dev` · **Date:** 2026-09-28
**Plan:** `plans/hydrocouple/DIFFERENTIABLE_INTERFACE_ALTERNATIVES_2026-09-28.md` (rev 3)
**For:** an agent or person with a real machine: a Mac (the author's), and
ideally one CUDA box for the device rows.

## What this round claims

1. **Tensors cross the boundary without copies (G0).** `get_values_into` /
   `set_values_from` on every C++ data-item wrapper accept any DLPack
   producer (PyTorch, CuPy, JAX-as-source, NumPy) on any device. The C++
   item receives a `BufferDescriptor` over the tensor's own memory. A C++
   engine calling a *Python* item with device memory hands it a
   `hydrocouple.dlpack.BufferView`, which `torch.from_dlpack` aliases.
2. **The interface has a derivative contract and is still header-only and
   standard-library-only (G1).** `Capability::Differentiable`,
   `DifferentialRole`, `DifferentialEntry`, `DifferentialSet`,
   `IDifferentiableModelComponent` (`vjp`/`jvp` of the most recent step,
   with state items so gradients flow through time). ABI version stays 2:
   purely additive (a new side interface; an enum value appended).
3. **Gradients cross model boundaries in both frameworks (G3-lite).**
   `hydrocouple.torch.Step` (`torch.autograd.Function`) and
   `hydrocouple.jax.Step` (`jax.custom_vjp`) drive a C++ component's
   `update()` forward and its `vjp()` backward. The flagship test chains
   **torch network → C++ reservoir → C++ reservoir → torch head** over six
   steps; one `loss.backward()` gives gradients for the network (upstream
   of two C++ models), both C++ parameters, the head, and the initial
   storage (reachable only through time). All match central finite
   differences taken through forward runs only; JAX agrees with PyTorch to
   1e-12; a network upstream of both C++ models is recovered from data
   (loss falls >95% in 40 epochs).

### Things that can only go wrong on the Mac, and what they look like

1. **`dynamic_cast` across images (clang/libc++).** The overlays reach
   `IDifferentiableModelComponent` and `ICheckpointableModelComponent` by
   `dynamic_cast` from a component created inside a `dlopen`ed `.dylib`.
   The header's `#pragma GCC visibility push(default)` (commit 5ac202c)
   covers the new class, so this should hold. If it does not, every
   gradient test fails with `TypeError: component 'cpp-reservoir' does not
   implement IDifferentiableModelComponent` although `capabilities()`
   lists `Differentiable`. Report it; do not work around it in the tests.
2. **The fixture compiler.** `tests/test_gradients.py` compiles
   `cpp_component/reservoir_component.cpp` with the first of `g++`,
   `clang++`, `c++` on `PATH` (on macOS `g++` is Apple clang). A compile
   failure prints the compiler's stderr.
3. **JAX on Apple silicon** installs a CPU `jaxlib`; that is all these tests
   need. `jax-metal` is not required and not tested.
4. **MPS.** *(Verified 2026-09-28: a torch 2.14 MPS float32 tensor exports
   `(kDLMetal, 0)`; after `set_accelerator(DLDeviceType.Metal)` the probe
   receives `MemorySpace.Device`, device 0, the tensor's own pointer and
   byte strides, and refuses it as host-only. Script:
   `verification/g0g1/mps_probe.py`.)* `TestRealDevice` only looks for CUDA. PyTorch's MPS tensors
   export `kDLMetal` via DLPack in recent versions; if you want the device
   rows on the Mac, try `probe.item.get_values_into(torch.zeros((3,4),
   dtype=torch.float32, device="mps"), (0,0), (3,4))` and confirm
   `probe.last["space"] == 2` (Device). This is exploratory, not a gate:
   float64 is not supported on MPS and the probe is Float64-only.

## The device rows (a CUDA machine)

`TestRealDevice` in `tests/test_dlpack.py` runs only when
`torch.cuda.is_available()`:

- `test_a_device_tensor_is_lent_not_copied`: a CUDA tensor reaches the C++
  probe as `MemorySpace.Device`, device id = `t.device.index`, address =
  `t.data_ptr()`.
- `test_a_torch_component_receives_device_memory_it_can_write`: C++ calls a
  Python item with a device descriptor; the item gets a `BufferView`,
  `torch.from_dlpack` aliases the same pointer, and writes land.
- `test_an_explicit_stream_is_accepted`: a producer on a non-default stream
  with `stream=` passed through.

**Stream semantics are the one open question these rows touch.** The
interface has no stream notion; the bindings' contract is host-synchronous
(when `get_values_into` returns, the values are in place). With `stream=None`
a CUDA producer syncs to the legacy default stream. A real SDK device item
must either work on that stream or synchronise before returning. Please
report whether the stream row passes, and whether it still passes with
`CUDA_LAUNCH_BLOCKING=0` and a deliberately slow producer kernel on stream
`s` (e.g. a large `torch.cumsum` launched on `s` just before the call). If
the values read are stale, that is the gap plan §9 names, and it is an
interface question (a stream/event field or a completion rule), not a
bindings bug.

## Falsifiers

`verification/g0g1/falsify.sh` plants 23 faults, one at a time, and
requires the named gate to fail: 10 in the DLPack and inbound bridges
(strides as elements, dropped device id, pinned-as-pageable, ignored
read-only flag, a capsule destructor that swallows a pending exception,
unfolded `byte_offset`, a leaked borrow, device memory handed to NumPy,
unrevoked lent views, JAX arrays accepted as destinations); 7 compiled into
the C++ adjoint (`HC_FALSIFY_*` in `reservoir_component.cpp`: a sign
error, a dropped state cotangent, the wrong linearization point,
accumulate-instead-of-write, a dropped `jvp` term, each caught by a
finite-difference or adjointness gate); 4 in the overlays (no replay,
dropped state gradients in torch, zeroed state cotangent in JAX, dropped
`StateAfter` seeds); and 2 against the interface invariants (a
`<dlpack/dlpack.h>` include in `hydrocouple.h`; a C++-only enum reorder).

Harness rules, learned the hard way this round:

- **`--force` on every rebuild.** setuptools does not track headers
  reached through other headers (`py_component_bridge.h` →
  `py_data_item_bridge.h`). Without `--force`, a header-only mutation is
  silently not compiled and reads as a survivor (D9 did exactly that on
  the first run).
- **"Does not build" is checked against the baseline.** If a mutant fails
  to compile, the script restores it and rebuilds; if the clean tree also
  fails, it stops with `BROKEN` instead of reporting every later row as
  CAUGHT (a mid-run `pyproject.toml` edit did exactly that on the second
  run).
- An empty selection is `NO SUCH GATE`, a failure.

Two rows (D3, D8) are caught by a **segfault**: with the fault in, the
harness dereferences a fake device address, which is precisely the harm
the guarded code prevents. That is a correct catch, and it is also why
the guarded code must not regress. On CPython 3.13 (the Mac run) D5 is
caught by a crash as well: an exception lost during unwinding leaves the
interpreter in a state 3.13 does not survive, where 3.11 reports a
`SystemError`. Same verdict, different mechanism.

**Test counts vary by one with the tree.** `test_interface_purity.py`
parametrizes over `include/*.h`, so a generated `include/version.h` in the
source tree (present on the Mac, absent on a fresh clone) adds one passing
row: 182 rather than 181. That is intended: `version.h` is installed with
the interface and its includes are held to the same rule.

## Out of scope for this round (and where it lives in the plan)

- **A Python component's `vjp` visible to C++** (the bridge direction for
  `IDifferentiableModelComponent`, Torch-derived). G3 proper.
- **`IDifferentiableAdaptedOutput`.** Deferred to G2, where the SDK's
  adapters give it something to test against; an untested interface is not
  added.
- **The C++-driven engine** (LibTorch autograd in the SDK, Revolve over
  checkpoints). G2.
- **JAX under `jit` with ordered effects.** Today the step order under
  `jit` rests on the data dependence through the state; the gate proves
  it for a time loop. An FFI/ordered-effect path is G3 proper.
