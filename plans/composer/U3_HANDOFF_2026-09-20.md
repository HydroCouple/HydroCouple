## 2. Two deviations from the plan, both deliberate

**Markers are solids, not screen-sized billboards.** The plan asked for
"screen-sized camera-facing quads … through a third pipeline (a sampler-free
quad with a per-instance centre, size from the uniform block)". That is a new
`.vert`/`.frag` pair, a qsb compile step and a third pipeline — none of which I
can compile, run or look at from here, and all of which would reach you
unverified. A solid octahedron needs **no new pipeline and no new shader**: it
is correct from every angle, lit by the material already there, and its geometry
is checkable and checked. Size is in map units, automatic from the layer's
extent (a fiftieth of the diagonal) or set per layer.

If you want true screen-sized billboards later, that is a shader slice worth
doing *on the Mac*, where it can be seen. The geometry side would not change.

**Full U3b is deferred, and U3b′ does the job that matters.** The plan wanted
`DataItemLayer` to delegate to a shared prism/surface builder extracted from
`MeshLayer` — a refactor of a 1,835-line file with 27 gates on it that I cannot
run. Instead, filled convex rings close the same defect for the case that
actually arises: **a mesh face is always convex**, so a component's
face-attached output now draws as a surface. What is *not* covered is a layered
data item peeling as prisms; that remains a `MeshLayer` refactor and should be
done with the build in front of you. Recorded in the plan under U3.

## 3. Two real defects my own gates caught

Running the gates — not just compiling them — found both:

**The degenerate-`QRectF` trap, for the fourth time in this program.** Marker
size came from the layer's extent, guarded by `box.isEmpty()`. A row of gauges
along a river is collinear, so its extent has height exactly zero, and QRectF
calls that empty — **every collinear point layer drew nothing**. Now the
diagonal decides. D26 (`extentmath`), C4a (point bounds) and C2 (`MeshSpatialGrid`)
each paid for this same rectangle; `PointsInARowStillHaveAnExtentToSizeFrom` is
the gate, and mutation M2 restores the bug.

**An empty batch is not nothing.** The point branch appended its batch
unconditionally, so a layer that drew no markers still handed the renderer a
batch to upload and draw zero triangles from. Appended only when non-empty now,
as every other batch in that function already was.

## 5. Look at it

```bash
build/darwin/composer_screenshot artifacts/composer-markers.png --scene
```

Then in the app:

1. Add a point layer (a gauge shapefile, or *From Components* on a component
   with a point output). Switch to **3D**: the points are there as solids,
   sitting on the terrain if a mesh is loaded. Before U3 this view was empty of
   them.
2. **Layer Properties ▸ Rendering** on that layer: *Marker size* reads
   "Automatic". Type 50 — they grow. Set it back to 0 — automatic again.
3. A layer with one point only draws nothing and the size reads Automatic:
   there is no extent to scale from, and guessing between metres and degrees is
   guessing by 10⁵. Give it a size and it appears.
4. Add a mesh whose values are on **nodes**. In 3D it used to be blank; now it
   is a cloud of coloured markers.
5. A polygon layer: **Rendering ▸ Fill rings as faces in 3D**. A mesh-face
   layer fills into a surface; a catchment boundary (concave) stays an outline —
   that is the convexity rule, not a failure.
6. **A layered mesh** (FVQual output, or a layered UGRID file): Rendering now
   has *Show layers from* / *…down to*. Peel to a single layer and the water
   column opens up. Try to set the range backwards — it will not invert.
7. Selection still crosses views (U6): click a marker in 3D and the canvas
   selects the component that produced it.
