## 2. The split, and why the gates exist at all

`describeArgument()` needed a loaded component library, so B5a's
classification chain has never been testable without a build. It is now
two halves:

- **gathering** — the `dynamic_cast`s and the
  `validComponentDataItemTypes()` scan; still needs a component, still
  `test_configurator`'s to prove;
- **`chooseEditorKind(ArgumentFacts)`** — pure, total, and where every
  ordering decision lives.

The order is the thing that can be wrong, and the order is pure logic.
`tests/gui/test_argumentkinds.cpp` links against no component, no widget
and no GDAL, and **ran here**.

Note what `ArgumentFacts` does *not* contain: the argument's id and its
caption. B5a's rule that nothing may be decided from those is now
enforced by the type rather than by discipline — the chooser cannot
consult them because it is never given them.

## 3. The decisions, in order, and why each is where it is

1. **Typed interfaces first.** A component implementing
   `IPolyhedralSurfaceComponentDataItem` has *told* us its argument is a
   surface; deciding from rank instead calls it a table and hands the
   user a spreadsheet of coordinates.
2. **Space beats time.** A time-varying mesh is a mesh whose values move:
   the geometry is the hard thing to edit and a time axis can be a column
   inside that editor, whereas a time-series editor has nowhere to put
   twelve thousand faces. HydroCouple names this combination
   (`ITimeSeriesPolyhedralSurfaceComponentDataItem`), so it is not
   hypothetical.
3. **Time beats identifiers.** A table of series is worth plotting
   against its time axis; the ids are its rows.
4. **Categorical before rank**, unchanged — a choice is a choice whether
   it holds one value or a hundred, and a *grid* of categorical values is
   still a table, because a combo box holds one thing.
5. **Duration before Quantity.** A unit whose dimensions are time and
   nothing else is a length of time: "3600 s" wants an editor that can
   also say "1 h". A velocity or a frequency is not a duration.
6. **Crs from the component, not the caption.** `validComponentDataItemTypes()`
   naming `ISpatialReferenceSystem` is the component saying so. The plan
   left this conditional on a signal existing (R3) — it does.
7. **Text from a file is text.** FVQual's kinetics block takes a `.rxn`
   file but what the user edits is its contents, so a `String` scalar
   with file filters gets the text pane. Its dialog must keep a file
   chooser, which makes this judgement free if it is wrong either way.

**`DateTime` is deliberately not implemented.** There is no `DataKind`
for it and nothing distinguishes a Julian-day scalar from any other
`Float64`. Inventing a signal would violate R3 exactly as it would have
for Crs. If the SDK grows one — a value definition, or a unit dimension
convention — it drops in as one more clause. Recorded rather than
quietly skipped.

## 4. The regression this slice could have shipped

Widening the enum meant nine kinds that matched no `case` in
`componentconfigurator.cpp`'s switch. No `default:`, so they would have
produced no widget, hit the `if (!editor) continue;` and **disappeared
from the component's form** — a component's meteorology simply gone,
with the build green.

So the descriptor now carries two kinds. `kind` is what the argument
*is*; `inlineKind` is what the dock draws until that kind has a dialog,
and it is the pre-U2a chain kept verbatim. The switch reads `inlineKind`.
`NoArgumentLosesTheEditorItUsedToHave` enumerates every combination of
the flags that matter and asserts the fallback is always something the
dock can draw; `TheFallbackIsExactlyTheOldChain` asserts untyped
arguments look exactly as they did.

**Each dialog that lands in U2b/U2c moves one kind from `inlineKind` to
`kind`.** When the last one lands, `genericEditorKind` and `inlineKind`
both go.

`genericEditorKind` is deliberately a *copy* of the old chain rather than
a call into the new one with the typed flags cleared: the two are
supposed to diverge — that divergence is the feature — and expressing one
in terms of the other would make every future change to the new chain
silently change the fallback.

## 6. Build, test, falsify

```bash
cmake --build --preset Darwin 2>&1 | tee verification/u2/build.log
ctest --preset Darwin --output-on-failure 2>&1 | tee verification/u2/ctest.log
BUILD=build/darwin verification/u2/falsify_kinds.sh 2>&1 | tee verification/u2/falsify_kinds.log
```

`test_argumentkinds` is new and registered.

Watch **`test_configurator`**. It is the suite that exercises the
gathering half, and its fixture component's arguments may now describe to
different `kind`s than before — that is the point. Their `inlineKind`
should be unchanged, and so should every widget the dock builds. If a
case asserts on `descriptor.kind` where it means "what is drawn", it
wants `inlineKind`; tell me which and I will say whether the gate or the
code is wrong.

## 7. Look at it

There is nothing new to *see* yet — that is honest, and it is why this is
a foundation slice. What you can confirm is that nothing changed:

1. Open a composition with FVQual configured. Every argument row draws
   exactly what it drew before: same widgets, same values, same order.
2. Edit each one and save. The document payloads are unchanged.
3. A component with a mesh or time-series argument still shows its table
   rather than an empty row — that is `inlineKind` doing its job, and it
   is the thing most worth checking.
