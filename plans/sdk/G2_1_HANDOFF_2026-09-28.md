# Hand-off: G2.1 — reverse-mode differentiation of a composition, in the SDK, without LibTorch

**Repos:** HydroCouple (`dev`), HydroCoupleSDK (`removing_qt`) · **Date:** 2026-09-28
**Plan:** `HydroCouple/plans/hydrocouple/DIFFERENTIABLE_INTERFACE_ALTERNATIVES_2026-09-28.md` (G2, split into G2.1–G2.3)
**For:** the Mac verifier.

## What this round claims

A composition driven from C++ — no Python, no LibTorch — can be run
forward and then differentiated backward, and every gradient it returns
equals central finite differences taken by re-running the composition
forward from scratch. Concretely:

1. **Interface (HydroCouple):** `IDifferentiableAdaptedOutput` — the
   adapter's counterpart of `IDifferentiableModelComponent` (the adapter
   is `Output`, its adaptee `Input`, its arguments `Argument`; stateless
   adapters only). Standard-library-only; ABI version stays 2.
2. **SDK:** `LinearTransformAdaptedOutput` (unit conversion) implements it:
   x̄ = m·ȳ, m̄ = Σȳx, b̄ = Σȳ, and the tangent.
3. **SDK:** `Differentiation::DifferentiableWorkflow`, a
   `TimeSteppedWorkflow` that checkpoints every component before every step
   and runs `backward(seeds, gradients, message)`: recorded steps
   last-first, schedule last-first; output cotangents in, input cotangents
   routed back along each connection *through every adapter's own vjp* to
   the provider's root output, where they are **added** (fan-out); argument
   cotangents summed over steps; state cotangents carried to the previous
   step and returned as initial-state gradients; every step but the last
   replayed from its checkpoint; the composition restored afterwards.
4. **Refusals, by name, before any work:** feedback loops (iterative
   coupling is G2b), non-differentiable components, stateful adapters on a
   connection (relaxation, temporal interpolation), a consumed output its
   provider does not differentiate, multi-inputs, >1 step without
   `Checkpointing`, a component that finished before the others, and a
   `restoreState` that leaves a component finished.

## The acceptance composition

```
         ┌──── LinearTransform (m, b) ───► B ──► loss
    A ───┤
         └───────────────────────────────► C ──► loss
```

Three nonlinear reservoirs with state, eight steps. `A`'s outflow reaches
the loss along two connections, so its cotangent must be a sum. Gates in
`tests/hydrocouplesdk/test_differentiation.cpp` (16):
`EveryGradientMatchesFiniteDifferences` (kA, kB, kC, the adapter's
multiplier and offset, the initial storage of A and B, i.e. 17 numbers,
each against a central difference of full forward runs),
`ZeroIsNotAGradient`, `EveryStepButTheLastIsReplayedOnce`,
`BackwardLeavesTheCompositionWhereItFoundIt` (and the run continues
identically), `ASecondBackwardAgreesWithTheFirst`, the adapter's own
adjoint vs FD plus adjointness, and one gate per refusal.

## Build and run on the Mac

The SDK finds the interface either as an installed CMake package
(`find_package(HydroCouple)`, whatever your `CMAKE_PREFIX_PATH` points at)
or, failing that, as the sibling checkout's `../HydroCouple/include`. The
configure log says which ("HydroCouple interface package found: …"). If it
is the package, reinstall the interface first so it carries
`IDifferentiableAdaptedOutput`:

```sh
cd HydroCouple && cmake --build build && cmake --install build --prefix install/Darwin   # only if the package is used
cd ../HydroCoupleSDK
cmake --preset macos-full && cmake --build build --parallel
./build/tests/HydroCoupleSDKTests --gtest_filter='Differentiation*'     # 16 passed
./build/tests/HydroCoupleSDKTests --gtest_brief=1                     # expect 284 + skips, 0 failed
BUILD=build verification/g2/falsify.sh                                # 16/16 CAUGHT, ~2 min
```

A stale interface shows up as a compile error in
`lineartransformadaptedoutput.h` (`IDifferentiableAdaptedOutput` not
declared); it means the SDK is reading an old install.

## Known limitations (deliberate, documented in the header)

- **Inputs poked from outside between steps are not recorded.** A replay
  sees their *current* values. Boundary conditions must come from inside a
  component (its own time series, restored with its checkpoint), which is
  how a real model works; the test's forced reservoir does exactly that.
  If drivers turn out to poke inputs in practice, the engine can snapshot
  unconnected inputs per step — a small follow-up.
- **Memory is O(N) checkpoints** (one token per component per step).
  Revolve's O(log N) is G2.2.
- **Float64 only**; host buffers only inside the engine.
- **Seeds read the composition at step n.** When the seed function runs
  for step *n*, the composition has been replayed to step *n*, so the loss
  cotangent can be computed from the outputs as they are — the test does.

## What comes next

- **G2.2 Revolve**: checkpoint every k-th step (binomial schedule),
  recompute the rest; gate that checkpoint count grows as log N while every
  gradient is unchanged.
- **G2.3 LibTorch layer** (`HYDROCOUPLESDK_WITH_TORCH`): the composition as
  one `torch::autograd::Function` (loss and parameters in C++ Torch), and an
  `AtenDifferentiableComponent` base whose `vjp` comes from
  `torch::autograd::grad` — new physics with no hand-written adjoint.
- **G2b iterative coupling**, and adjoints for the stateful adapters (their
  derivative spans steps; the contract needs adapter state first).
