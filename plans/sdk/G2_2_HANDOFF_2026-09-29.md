**Repo:** HydroCoupleSDK (`removing_qt`) · **Date:** 2026-09-29

## What this round claims

`DifferentiableWorkflow` can differentiate an N-step run while holding
**O(log N)** composition checkpoints instead of N, and the gradients are
**bit-for-bit identical** to the every-step engine of G2.1.

- `setCheckpointPolicy(CheckpointPolicy::Logarithmic)` (default stays
  `EveryStep`, G2.1's behaviour: N checkpoints, N − 1 replays).
- **Forward (online, N unknown in advance):** after each step the engine
  keeps a dyadic ladder — checkpoint k survives when k is a multiple of the
  largest power of two not above its distance from the newest checkpoint.
  At most two rungs per power of two; the first (k = 0) and the newest
  (k = N − 1) always survive; a dropped rung is never needed again.
- **Backward (offline per gap):** the last step is differentiated first
  (no replay); each gap between rungs is reversed by recursive bisection —
  recompute to the midpoint, hold it as a temporary, reverse the upper
  half, drop it, reverse the lower half. One temporary per level.
- **Metrics:** `storedCheckpoints()`, `peakCheckpoints()` (rungs + the final
  state backward returns to + temporaries), `replays()`,
  `checkpointedSteps()`.
- Switching to `Logarithmic` mid-run thins the existing record at once.

Why identical and not merely close: every step is still differentiated at
exactly its own linearization point; only the *order* in which primal
states are recomputed changes, and a restore from a checkpoint is exact.

## Measured (off-machine, two stateful reservoirs A → B)

| N | stored (ladder) | peak | replays | EveryStep: stored / replays |
|---|---|---|---|---|
| 10 | 5 | 8 | 15 | 10 / 9 |
| 100 | 8 | 15 | 344 | 100 / 99 |
| 1000 | 11 | 21 | 5 028 | 1000 / 999 |

Stored grows by ~3 per decade (log₂10 ≈ 3.3); peak stays within
stored + ⌈log₂N⌉ + 1; replays stay under N·⌈log₂N⌉ (5 028 vs 10 000 at
N = 1000). The test prints this table.

## Gates (5 new; 21 in `Differentiation*`)

- `TheLadderGivesExactlyTheSameGradients` — the G2.1 composition (A → unit
  adapter → B, A → C, 8 steps) under the ladder: every gradient `==` the
  EveryStep gradients (which G2.1 checks against finite differences).
- `CheckpointsGrowAsTheLogarithmOfTheSteps` — N = 10, 100, 1000: stored ≤
  2⌈log₂N⌉ + 2; stored + 1 ≤ peak ≤ stored + ⌈log₂N⌉ + 1, and peak >
  stored + 1 for N ≥ 100 (the metric cannot under-report); replays ≤
  N⌈log₂N⌉; first and newest rungs present; EveryStep: stored = N,
  peak = N + 1, replays = N − 1.
- `TheLadderAndEveryStepAgreeOverALongRun` — N = 300, gradients `==`,
  ladder stores < 1/10 as many checkpoints.
- `SwitchingToTheLadderMidRunThinsAtOnce`.
- `ASecondBackwardUnderTheLadderAgreesAndRestores` — no temporary survives
  a pass; the composition is back where the forward run left it.

## One interface gap this round exposed (for review, not fixed)

`ICheckpointableModelComponent` has `saveState` and `restoreState` but no
way to **release** a state. The ladder drops hundreds of tokens over a long
run; for a component whose token is the state itself (the test fixtures)
that frees the memory, but for one whose token names a *file* (the
interface's own suggestion: "under referenceDirectory()"), every dropped
rung is a file left on disk — O(N) disk behind an O(log N) ladder. A
`releaseState(token)` (default no-op in the SDK base) would close it. It is
an additive interface change, so it is the review's call; until then a
file-backed component should keep its checkpoints small or reuse paths.
