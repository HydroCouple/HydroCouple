## What it is

An optional layer, `HYDROCOUPLESDK_WITH_TORCH` (default **OFF**), built as a
separate library, **`HydroCoupleSDKTorch`**. The core `HydroCoupleSDK` never
includes or links LibTorch. With the option off, nothing changes.

It adds two pieces.

**1. `AtenModelComponent`** (`differentiation/torch/atenmodelcomponent.h`).
You write the physics once, as a function of tensors:
`step(states, inputs, arguments) -> {states', outputs}`. You write no
adjoint. The base class then:

- `update()`: pulls the inputs, gathers every differentiable item into a
  Float64 tensor (`getValuesInto`), and steps with no graph. It writes the
  results back (`setValuesFrom`) and keeps the linearization point.
- `vjp()`: re-runs `step()` from that point with autograd on and returns
  `torch::autograd::grad`.
- `jvp()`: uses the double-backward identity (the vjp is linear in its seed).
- Checkpoints: the token holds the step count, every state, and every
  Float64 output. `releaseState` is a no-op.

The step count is part of the token, so forcing indexed by `stepIndex()`
replays exactly.

**2. `TorchComposition`** (`differentiation/torch/torchcomposition.h`). It
presents a recorded composition run to LibTorch as **one autograd node**:
`trajectories = composition({k, m, S0, …})`, then `loss.backward()`.

- **Forward:** rewinds the workflow and writes the bound parameters,
  re-initializing any adapter so it latches its new arguments. It runs N
  steps and stacks each observed output as `[N, shape…]`.
- **Backward:** passes the incoming gradients to
  `DifferentiableWorkflow::backward()` as per-step seeds and returns the
  argument and initial-state gradients.

**Design point to review:** the plan's rev-2 text made Torch's graph the
tape, with one `Function` per component step. As built, G2.1's engine
remains the tape and Torch sees the whole run as a single node. Reasons:

- Hand-written vjps, adapter adjoints and ATen components all keep one
  routing and checkpoint implementation (EveryStep or the G2.2 ladder),
  which is already falsified.
- Torch never has to hold N steps of graph.

The outcome the plan asked for still holds: ATen-native physics is
differentiable by construction, and C++ LibTorch code can train through a
composition.

**Engine additions (Torch-free, in the core):**

- `DifferentiableWorkflow::rewind()` returns every component to the state
  before step 1 and releases the record. A training loop needs this,
  because the workflow lifecycle refuses to prepare a second time.
- **A fix:** a step in which a component *fails* used to drop the
  checkpoint taken before it without releasing it (a leak left over from
  the releaseState round). It is now released.
- The shared test component moved to `tests/hydrocouplesdk/reservoir_fixture.h`,
  so that both suites use it.

The cloud wheel is `torch 2.14+cu130`, and its `TorchConfig.cmake` fails
without a CUDA toolkit. The off-machine build therefore used the new
fallback, `-DHYDROCOUPLESDK_TORCH_ROOT=<site-packages>/torch`, which links
`torch_cpu` and `c10` directly. On the Mac, the CPU/MPS wheel's config
should load, so plain `find_package(Torch)` is the path to exercise there.

## Run on the Mac

Reinstall nothing: no interface change in this round.

```sh
cd HydroCoupleSDK
# 1. The lean build, as before (the engine changed: rewind, failed-step release)
cmake --build build-macos-full --parallel
./build-macos-full/tests/HydroCoupleSDKTests --gtest_filter='Differentiation*'   # 29
./build-macos-full/tests/HydroCoupleSDKTests --gtest_brief=1                     # 358 + 1 skip
BUILD=build-macos-full verification/g2/falsify.sh                                # 32/32, T rows SKIPPED

# 2. The Torch build: a separate build dir. LibTorch comes from the python3 that has torch.
python3 -c 'import torch; print(torch.__version__, torch.utils.cmake_prefix_path)'
cmake --preset macos-full -B build-macos-torch -DHYDROCOUPLESDK_WITH_TORCH=ON
cmake --build build-macos-torch --parallel
./build-macos-torch/tests/HydroCoupleSDKTorchTests                               # 20
otool -L build-macos-torch/libHydroCoupleSDK*.dylib | grep -i torch              # expect nothing
BUILD=build-macos-torch verification/g2/falsify.sh                               # 46/46
```

If `find_package(Torch)` fails on the Mac, report the error, then retry
with
`-DHYDROCOUPLESDK_TORCH_ROOT=$(python3 -c 'import torch,os;print(os.path.dirname(torch.__file__))')`.
That tells us whether the fallback is needed on macOS too.

Things worth a look:

- Does `--preset … -B` take the override on your CMake?
- Does the vcpkg toolchain in `macos-full` interfere with `find_package(Torch)`?
- Is the second falsifier run's wall time acceptable? Each row rebuilds
  both test targets.

## Open (not in G2.3)

- **Install/export:** `HydroCoupleSDKTorch` and its headers are build-tree
  only. Packaging needs to decide how an installed SDK finds the same
  LibTorch as the Python `torch` (§5.1).
- **CPU only.** Device tensors: the pending CUDA rows and the stream
  question.
- **The plan's G2 "tangible" named a temporal-interpolation adapter
  between the two components.** The SDK's interpolation and relaxation
  adapters are stateful and are still refused. Stateful adapter adjoints
  remain open.
- G2b (iterative coupling), G3 proper (Python face of the SDK engine).

## Mac result (2026-09-29)

All green: lean 358 + 1 skip and 32/32; Torch build 20/20 and 46/46; the
core `libHydroCoupleSDK` links no LibTorch. Record and logs:
`HydroCoupleSDK/verification/g2/` (f16a307).

- Plain `find_package(Torch)` works with the pip wheel on macOS (only the
  harmless "kineto not found" warning); `HYDROCOUPLESDK_TORCH_ROOT` is not
  needed there. `--preset … -B` honours the override; the vcpkg toolchain
  does not interfere.
- The first Torch-build falsifier run gave 45/46 (T3 "does not build", T7
  survived), and neither reproduced by hand. Cause: the harness rebuilt both
  test targets in one `cmake --build --target A B -j 8`; under Unix
  Makefiles that is one parallel make whose sub-makes rebuild the shared
  libraries concurrently. The Linux run used Ninja, which serialises them.
  Fixed in b84bca7 (one target per invocation); rerun 46/46, none caught by
  a build failure, under 5 minutes.
