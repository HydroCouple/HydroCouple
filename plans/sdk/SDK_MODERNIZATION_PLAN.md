## Phase 2 — Data-plane efficiency (2–3 weeks)

This phase implements interface-review items 1 and 6 inside the SDK (the upstream interface changes shipped as v2.0.0 — see Phase 3) and is the prerequisite for GPU, MPI, and fast IO alike. Backward compatibility is not required, so the rule is clean: **`hydrocouple_variant` no longer exists** — typed contiguous buffers are the only field-exchange mechanism, and metadata scalars use native types (`double` bounds/missing/default values, string category labels, string-encoded clone arguments). Note the interface repo's two governing principles, which the SDK must respect when proposing upstream changes: interface headers carry no executable code (shared conveniences go to the non-normative `hydrocouplehelpers.h`), and no speculative abstraction (vocabulary enters the standard only with a concrete consumer).

1. **Typed storage backends.** Extend the storage-mixin refactor (already started on this branch) so every component data item stores fields as contiguous typed arrays (`std::vector<double>` etc., 64-byte aligned) selected by `DataType`. Delete the variant `getValue/getValues/setValue/setValues` implementations and their per-index-kind overload sets outright; scalar convenience access becomes a typed template helper over the bulk path.
2. **`BufferDescriptor` bulk path.** Implement `getValuesInto/setValuesFrom` (`DataKind`, `int64_t` shape/strides, memory-space tag) with `memcpy` fast paths when layouts match and OpenMP-SIMD conversion loops otherwise. This is the currency later consumed by HDF5 writes, MPI packing, and GPU staging.
3. **Bulk spatial views.** Implement `IMeshView`-style SoA/CSR accessors over the quad-edge structures per `docs/IMPLEMENTATION_PLAN.md` §6–7 (node coordinate spans, `faceNodeOffsets/faceNodes` CSR) — deliberately UGRID-congruent so Phase 4 writers serialize views without transformation. Same for `IRegularGrid2D/3D` (coordinate spans, active-mask span) and temporal items (`std::span<const double> times()`).
4. **Error queue.** Port the persistent `ErrorQueue` design from the superseded roadmap (no Qt signals; `Signal<>`-based notification) — required by Phase 5 for cross-process failure propagation.

*Verify:* benchmark (Google Benchmark, in the `tests` vcpkg feature) capturing bulk-path throughput on a 10⁶-element exchange, with the pre-removal variant path measured once as the baseline (expect ≥5×); hyperslab correctness tests (start/count against known layouts, all `DataKind`s, strided and contiguous); `grep` gate proving no `hydrocouple_variant` reference remains under `src/**/exchangeitems*`, storage backends, or IO paths; no hot-path heap allocation under `valgrind --tool=massif` spot check.

## Phase 4 — IO abstraction (4–6 weeks)

Architecture copied from the proven openswmm.engine design: **owned-snapshot value semantics + bounded queue + single writer thread + pluggable format writers.**

1. **Writer infrastructure.** `HydroCouple::SDK::IO::IOutputWriter` (lifecycle: `initialize/prepare/update/finalize`, `int` error returns) + `IOThread` (one `std::mutex`, two condition variables, bounded queue with back-pressure, atomic error propagation, drain-then-join shutdown) + `Snapshot` (deep-copied SoA slices built from Phase 2 buffer views; move-only task). The simulation thread never blocks on a file handle; format writers never see concurrent calls.
2. **YAML/JSON model initialization — targeted at `IArgument`.** Arguments are the serialization unit: a component's entire persistent configuration flows through its `arguments()`, and the SDK never serializes component internals directly. `ModelInitializer` reads a composition document — components (library path, id) with a block of per-argument payloads, connections (output→input with adapted-output chains), workflow settings, output-writer configuration — in YAML (`yaml-cpp`, a core manifest dependency from Phase 1) or JSON (nlohmann, already present), one schema for both, validated with actionable error messages before any component is instantiated. Each argument block feeds `IArgument::initialize(value, JSON|YAML, message)`; persistence walks `arguments()` calling the symmetric `serialize()` (interface-review item 9), building on the `readData/writeData(nlohmann::json)` machinery the SDK's arguments already implement. YAML is handled by conversion to/from JSON at the boundary, so argument implementations only ever see one format. Same document persists back out (round-trip guarantee), covering "model initialization and persistence" with human-diffable files.
3. **HDF5/UGRID writer** (thread-safe as implemented for the SWMM engine). Port the `Default2DOutputPlugin` pattern: `Conventions="CF-1.11 UGRID-1.0"`, mesh-topology dummy dataset with `cf_role`, node-coordinate and `face_node_connectivity` datasets from Phase 2 mesh views, unlimited time dimension with chunk+deflate, `extendAndWrite` hyperslab appends, every field tagged `mesh=…`+`location=node|edge|face`. Thread safety comes from the single-writer IOThread, not from mutexing HDF5. Also adopt the engine's symbol-hiding lesson (hide vendored HDF5/SQLite symbols on macOS) since GUI hosts will link their own copies.
4. **GeoPackage writer** following the openswmm convention: standard `gpkg_*` conformance tables; feature tables for the composition's spatial data (geometry from the existing WKB structs, SRS from `ISpatialReferenceSystem` → `gpkg_spatial_ref_sys`); results as `simulations` / `variables` / `result_timeseries(simulation_id, object_type, object_id, variable_id, elapsed_time, value)` / `result_summary`; optional `observed_series`/`observed_values` for sim-vs-observed workflows. Reuse the engine's RAII kit design (`DbPtr`/`StmtPtr`/`Transaction` with statement-reset rollback), buffered inserts (~5000-row flush), `PRAGMA synchronous=NORMAL`, and the ≤16 KB DDL-chunk `static_assert` for MSVC.
5. **NetCDF/UGRID writer.** Revive `src/threadsafenetcdf` behind the IOThread (its ~100 `#pragma omp critical` sections become unnecessary once all calls land on one thread; keep a `std::mutex` for the rare cross-thread metadata query), then express the same UGRID layout as the HDF5 writer per `docs/IMPLEMENTATION_PLAN.md` §18.
6. **CSV writer** — trivial, useful for tests and small models; also serves as the reference `IOutputWriter` implementation.
7. **Public developer-facing API.** The whole IO layer ships as a documented public surface (`HydroCouple::SDK::IO`, installed headers, exported CMake targets), not internal plumbing: model developers use the same `IOThread`/`Snapshot`/`IOutputWriter` kit for their own engine outputs and the same argument serialization for their own configuration formats — one IO stack for the SDK and every component built on it. That makes its efficiency a contract, enforced by design rules: (a) large numeric payloads never transit a JSON/YAML DOM — the serialized form carries an external binary reference (URI + `DataKind` + shape inline; bulk bytes in a sidecar written zero-copy through `BufferDescriptor`, or CBOR/msgpack via nlohmann when a single self-contained file is wanted), with inline text arrays only below a small threshold (~1 KB); (b) writers consume `BufferDescriptor` views directly — no per-element conversion between a component's store and the file API; (c) snapshot deep-copies are the only copies on the write path, and reusable snapshot buffers avoid reallocation across timesteps; (d) parsing is single-pass with reserved containers — no repeated tree walks.

*Verify:* YAML↔JSON round-trip tests; HDF5 output validated by `ugrid-checks`/xarray+xugrid load in a CI Python step; GeoPackage opens in QGIS and passes `PRAGMA integrity_check` plus gpkg conformance queries; a writer-thread stress test (fast simulation, slow disk) proves back-pressure and clean shutdown; benchmark round-tripping a 10⁷-element argument via sidecar reference completes at near-`memcpy`/disk speed with flat memory (no DOM inflation); an example "developer's model" outside the SDK tree links only the installed targets and drives its own outputs through the public IO API; outputs written to reviewable `build/test-output/`.

## Phase 5 — Message passing: transport, proxies, virtual nodes (5–8 weeks)

Implements `docs/IMPLEMENTATION_PLAN.md` §22 — with one structural change per the review (G3): the envelope protocol, command-worker loop, proxy component, and status-propagation thread are all retained, but they sit **behind an `ITransport` abstraction** so MPI is backend #1 rather than the architecture itself.

1. **Transport layer.** `Transport` interface (endpoints, tagged send/receive, nonblocking variants returning `IExchangeRequest` handles) with three backends: `InProcTransport` (testing — the whole protocol unit-testable without mpirun), `MpiTransport` (inter-communicators per component group, exactly as §22.2), and a stub `TcpTransport` proving the seam for future cloud/gRPC/UCX work.
2. **Protocol.** The §22.3 fixed 32-byte envelope and op codes unchanged; `MPIValuePacker` generalized to `ValuePacker` operating on Phase 2 `BufferDescriptor`s so payloads are typed contiguous buffers, never per-element variants (efficiency on the wire equals efficiency in memory).
3. **Proxy and worker.** `ProxyModelComponent` (main rank) and `ComponentWorker` (event loop) per §22.5–22.7, plus the cloud-hardening from the review: connect/disconnect/isConnected, heartbeat op, request timeouts, and peer-death → proxy `Failed` + ErrorQueue entry (Phase 2.4).
4. **Local virtual node representation.** `PartitionedDataItem` implementing the review's `IPartitionedComponentDataItem`: owned/virtual global-index spans, owner-rank span, global↔local maps, and epoch counters. On top, a `HaloExchanger` that builds the send/receive pattern from ownership metadata at `prepare()` time and executes epoch-stamped nonblocking exchanges (begin → overlap compute → end). Encode the SWMM lessons as SDK policy: virtual entities carry no DOF (mirrors, reconstructed—not solved), exchange payloads support flux+derivative pairs (so implicit receivers keep stability), and decomposition eligibility rules are validated once, in one place, before run time.
5. **Workflow integration.** `WorkflowComponent` (the standard's `IWorkflowComponent`, currently unimplemented) orchestrating proxies and local components uniformly, with the §22.9 lifecycle walk-through as the acceptance script.

*Verify:* full protocol test suite on `InProcTransport` (no MPI needed in default CI); `mpirun -n 4` integration test — two coupled dummy components on disjoint ranks — matching serial results bit-for-bit; halo-exchange test on a partitioned grid verifying epoch correctness and overlap (timers show communication hidden behind compute); kill-a-worker test → proxy reports `Failed` with diagnostic.

## Phase 6 — GPU abstraction layer (4–6 weeks, gated on Phase 2)

Vendor-neutral, per decision — no CUDA types in public headers.

1. `MemorySpace`/`ExecutionContext` types and a `DeviceBufferRegistry` mapping data items to device allocations; `BufferDescriptor` gains device pointers naturally (tag was designed in from Phase 2).
2. Backend interface (`allocate/free/copy(src,dst)/synchronize` per space pair) with `HostBackend` always present and a `KokkosBackend` as the first accelerator implementation (vcpkg `gpu`/`gpu-cuda`/`gpu-hip`/`gpu-sycl` features, mirroring openswmm.engine's manifest) — Kokkos as an *optional backend behind the SDK's own abstraction*, not a public dependency.
3. Space-aware exchange: connection negotiation picks the cheapest legal path (same-device alias → peer copy → pinned staging → host), decided once at `prepare()`.
4. `ValuePacker`/`HaloExchanger` learn device buffers (pack on device, hand pinned staging to transport; direct GPU-aware-MPI path when `MpiTransport` detects support).

*Verify:* backend conformance test suite runs identically on Host and Kokkos backends; coupled-exchange test where producer field lives on device passes without an explicit user copy; benchmark shows device→device exchange beats naive host staging.

## Phase 7 — Missing implementations and meshing tools (6–9 weeks, parallelizable)

**7a — Spatiotemporal and id-based items (as before).** Implement the forward-declared-but-absent `HydroCouple::SpatioTemporal` data items (time-geometry, time-network, time-polyhedral-surface/TIN, time-raster, time-grid — now cheap: temporal dimension over Phase 2 typed stores); the id-based inputs/outputs (Qt-free successors of the Phase 0 deletions); and remaining items from `plans/IMPLEMENTATION_PLAN.md` §10.

**7b — Meshing tools library (`HydroCoupleTools`, namespace `HydroCouple::SDK::Tools`).** A first-class part of the package (`BUILD_TOOLS` + vcpkg `tools` feature), built on the SDK's spatial classes and emitting IMeshView/UGRID-congruent structures directly consumable by the IO writers and exchange items:

1. **Unstructured triangulation (2D).** Constrained Delaunay triangulation via CDT (MIT; the Phase 0 replacement for Triangle): domain boundary + constraint segments + region markers with per-region max-area/quality controls, hole support, and refinement. Output: SDK `TIN`/mesh views.
2. **Quad and quad-dominant meshing (2D).** Structured quad patches where the domain decomposes cleanly, and an indirect tri→quad path (pair-merge with quality thresholds, remaining triangles kept — quad-dominant) for general domains. Output: mixed-element polyhedral surface with UGRID `face_node_connectivity` fill values.
3. **Curvilinear structured grids (2D and 3D).** Boundary-fitted grid generation on four-sided (2D) / six-faced (3D logical block) domains: transfinite interpolation for the initial grid, optional elliptic (Winslow/Thompson) smoothing with orthogonality and spacing control, and grading/stretching functions along parametric directions. Output: SDK curvilinear grid classes (extending the regular-grid family) with full UGRID export.
4. **Terrain-following sigma grids (2D-vertical and 3D).** Vertical layer generation over a terrain/bathymetry surface: classic sigma stretching (uniform, Song–Haidvogel-style theta stretching, and user-supplied distribution functions), configurable layer counts, minimum-thickness enforcement in shallow regions, and optional hybrid z-sigma transition depth. Works over any horizontal mesh from 1–3 above (tri, quad, curvilinear): the generator extrudes the 2D mesh into layered 3D cells whose node elevations follow the terrain, producing prisms/hexahedra tagged with layer metadata (CF `ocean_sigma_coordinate`-style parameters carried through the UGRID/HDF5 writer).
5. **Terrain sampling and interpolators.** Elevation assignment from rasters (GDAL-gated) or scattered points (IDW/natural-neighbor over the triangulation), used by the sigma extrusion and standalone.

*Verify:* generator unit tests assert element quality metrics (min angle, aspect ratio, orthogonality deviation, positive Jacobians for curvilinear/sigma cells) and topology invariants (Euler characteristic, watertight connectivity); sigma grids validated for monotone layer interfaces and minimum thickness over synthetic and DEM-derived terrain; every generated mesh round-trips through the UGRID/HDF5 writer and loads in xarray+xugrid in CI; an example composes generator → exchange item → writer end-to-end.

*Verify (7a):* §10's table reaches zero unimplemented rows or documented won't-implement; spatiotemporal items covered by round-trip tests through both HDF5 and GeoPackage writers.
